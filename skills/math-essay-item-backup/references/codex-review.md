Codex 적대적 검증(필수 단계) 실행 방법과 프롬프트 틀.

## 왜 필수인가

이 스킬의 자체 검증 에이전트는 같은 모델이므로 **같은 맹점을 공유한다.** 실제로 이번 개발에서 자체 검증을 통과한 뒤 Codex가 잡아낸 결함이 여러 건 있었다. 대표적으로 파티팩의 인과 오류 — 문서가 "두께를 고정했기 때문에 넓이의 비만으로 한 변을 구할 수 있다"고 썼는데, 한 변은 두께와 무관하게 정해지고 두께 조건이 바꾸는 것은 부피였다. 자체 검증 두 겹이 이것을 놓쳤다.

## 실행

```bash
OUT="${OUT:-$(mktemp -d)}"   # 검토 자료와 결과를 둘 폴더 — 또는 작업 폴더 경로를 직접 지정
codex exec --skip-git-repo-check "<아래 프롬프트>" < /dev/null \
  > "$OUT/codex_review.md" 2> "$OUT/codex.err"; RC=$?
```

- `< /dev/null`을 빼면 **stdin을 기다리다 멈춘다.** 반드시 붙인다.
- **종료 코드를 그 자리에서 받아 둔다**(`RC=$?`). 다음 명령을 하나라도 끼우면 `$?`가 덮인다. 종료 코드와 결과 크기를 어떻게 판정하는지는 §결과 처리 0번에 있다.
- 출력을 파일로 리다이렉트한다. `tail`로 일부만 보면 잘린다.
- `run_in_background: true`로 실행한다. ultra 효율에서 10분을 넘길 수 있다.
- 모델·추론 강도 플래그를 붙이지 않는다. `~/.codex/config.toml`에 최고 설정이 박혀 있다.

## 검토 자료 준비 — `tools/make_review_input.py`

Codex는 이 대화를 모른다. 슬롯 JSON을 그대로 주면 읽기 어려우므로 **섹션 구분자를 넣은 평문**으로 만들어 준다. **도구가 만든다. 손으로 만들지 않는다.**

```bash
S=<스킬 루트>; WORK=<작업 폴더>
python3 "$S/tools/make_review_input.py" "$WORK/content.json" "$WORK/review_input.txt"
```

- 둘째 인자를 생략하면 슬롯 JSON 옆에 `review_input.txt`를 만들고, 폴더를 주면 그 폴더 안에 만든다.
- 표준 라이브러리만 쓴다.
- 산출물은 작업 폴더에 만들며 **스킬 폴더 안으로는 쓰지 않는다.** 동봉 예시(`examples/valid-similarity-20pt.json`)로 돌려 볼 때는 출력 경로를 작업 폴더로 반드시 준다 — 안 주면 종료 코드 2로 막는다.

기대 출력:

```
씀: /…/review_input.txt (47720바이트)
슬롯 JSON 키 71개 / 출력에 실린 키 71개
  누락 0건 · 잉여 0건 · 중복 0건
채점기준표 21행 · 배점 값 원문 그대로(단위 덧붙임 없음)
자체 점검 통과.
```

**「자체 점검 통과」가 찍히지 않으면 그 파일로 검토를 돌리지 마라.** 종료 코드가 0이 아니고, 어떤 키가 빠졌는지·몇 행의 배점이 어떻게 왜곡됐는지 이름을 대며 죽는다. 점검이 있는 이유는 실사용에서 난 두 사고다.

- 예전에는 이 문서가 스크립트를 **본문에 싣고 "복사해 쓰라"** 고 했다. 슬롯 키 목록(`order`)이 문서에 박혀 있어 새로 생긴 `_rubric_atoms_note`가 **검토 자료에서 통째로 빠진 채** 세 세트가 돌았다. 도구는 키 목록을 갖고 있지 않다 — 슬롯 JSON에 있는 키를 **전부** 싣고, 순서를 아는 키는 제자리에, 모르는 키는 마지막 「그 밖의 키」 묶음에 넣은 뒤 그 이름을 보고한다. `std3_text`·`lesson6_act`처럼 번호만 늘어난 키는 저절로 제자리로 간다.
- 예전 스크립트는 배점을 `f"{r['score']}점"`으로 찍어 합계 행의 `"20점"`이 **`"20점점"`** 이 되었고, Codex가 이것을 오탈자 결함으로 보고했다. **생성기 버그가 가짜 지적을 만든 것이다.** 도구는 값에 단위를 덧붙이지 않고, 자체 점검이 출력의 배점 열을 되읽어 원문과 글자까지 대조한다.

출력 형식은 `########## 묶음 ##########`으로 아홉 묶음(과제 개요 → 성취기준·성취수준 → 문항 정보 → 학생 지면 → 예시답안 → 채점기준 → 유의점 → 성취수준 구간 → 차시)을 나누고, 그 안에서 `===== [슬롯 키] =====`로 키를 나눈다. `_` 접두 키(`_rubric_atoms_note`·`_alignment_note`·`_figs`·`_flat_cond`…)는 지면에 인쇄되지 않지만 검토에는 필요하므로 `(내부 주석 — 지면 밖)` 표시를 달아 싣는다. `rubric_rows`는 열을 `|`로 나눈 표로 펴고, 셀 안의 줄바꿈은 ` / `로 이어 붙인다(문항 열의 성취기준 코드·평가 요소가 잘리지 않는다).

## 프롬프트 틀

`<...>` 자리를 채워 한 덩어리 문자열로 넘긴다. 확정 수치를 반드시 인라인한다 — Codex가 독립 재계산할 기준값이 된다.

```
당신은 한국 <중학교|고등학교> 수학 서·논술형 평가 전문가다. 아래 파일은 <학년> <단원> <수행평가|지필평가>(<서술형 n문항+논술형 m문항>, 총 <총점>점) 자료 전체다: <review_input.txt 절대경로>
(########## 로 아홉 묶음을 나누고 ===== [슬롯 키] ===== 로 키를 나눈다: 과제 개요, 성취기준과 성취수준, 문항 유형·형식·평가 요소, 학생 지면(도입·자료·발문·조건), 예시답안, 채점기준표, 채점·피드백 유의점, 성취수준 점수 구간, 차시 계획·평가. `_` 접두 키는 지면에 인쇄되지 않는 내부 주석이며 검토 근거로만 쓴다 — 그 문장의 문체·오탈자는 지적 대상이 아니다.)
파일을 직접 읽고 다음을 검토하라.

[확정 수치]
<모든 확정 수치를 나열. 예: 지름 24/30/36cm, 두께 2/2.5/3cm, π=3.14, 1인분=미디엄 1/4판 부피, …>

[검토 관점]
1. 수학적 정확성 — 모든 수치를 직접 재계산해 검증하라. 오답 경로의 값까지 확인하라.
2. 채점기준의 급간 완결성 — 각 채점 요소의 급간이 상호 배타적이고 빈틈없는가. 두 급간에 동시에 걸리거나 어느 급간에도 안 걸리는 답안을 실제 시나리오로 구성해 시험하라. <평가 유형에 맞는 문장 하나만 남길 것 — 수행평가: "이 평가는 수행평가이므로 0점 급간이 없고 최저 1점 급간이 백지·완전 오답까지 포괄해야 한다. 요소 배점은 2~4점이고 1점 요소는 없어야 한다." / 지필평가: "이 평가는 지필평가이므로 각 요소에 0점 급간이 정확히 1건 있어야 하며, 그 진술은 글자·띄어쓰기·마침표까지 정확히 `무응답 또는 그 외의 오답.`이어야 한다(포괄만으로는 불충족 — 문자열이 다르면 결함으로 보고하라). 각 요소의 급간 점수는 배점 s부터 0까지 1씩 연속이어야 하고, 채점기준표 데이터 행 수 = Σ(요소 배점 + 1) = 총점 + 요소 수다. 지필평가에서는 1점 요소를 허용한다.">
   단, 학교 학업성적관리규정 오버라이드가 있으면 위 고정 문구·급간 수·최저 배점 대신 그 규정의 확정값으로 검사하라 — 규정이 0점 문구를 달리 정하면 그 문구가 고정 문구가 된다. <오버라이드 확정값 또는 `없음`>
3. 발문·조건·예시답안·채점기준·유의점·성취수준 구간의 상호 정합. 배점 표기가 모든 자리에서 일치하는가.
4. 성취기준 정렬 — 선언한 성취기준을 실제로 가르치고 평가하는가. 평가 요소와 무관한 요소가 채점기준에 들어 있는가.
5. <학교급> <학년> 수준 적정성 — 학년 범위를 벗어나는 개념이 필요해지는 지점이 있는가.
6. 제출용 완성도 — 남아 있는 개발 흔적, 군더더기, 어색한 문장.

[출력 형식] 심각도별로: (A) 치명 오류(수학·정합 파손) / (B) 개선 권고 / (C) 사소한 다듬기.
각 항목에 위치(섹션 키)와 그대로 붙여 쓸 수 있는 구체 수정안을 적어라. 문제없는 관점은 '이상 없음' 한 줄로. 한국어로.
```

## 결과 처리

0. **종료 코드와 산출 파일 크기를 먼저 본다.** 둘 중 하나라도 어긋나면 — **종료 코드가 0이 아니거나, `codex_review.md`가 0바이트이거나** — 검토를 받은 것이 아니다. **검증 통과로 적지 말고 실패로 처리한다.** 크기를 안 보고 "지적 없음"으로 넘기지 마라.

   ```bash
   # RC은 §실행에서 codex 명령 바로 뒤에 받아 둔 값이다. 여기서 $?를 다시 읽지 마라 — 이미 덮였다.
   SZ=$(wc -c < "$OUT/codex_review.md" | tr -d ' ')
   printf '종료 코드 %s · 결과 %s바이트\n' "$RC" "$SZ" | tee "$OUT/codex.status"
   [ "$RC" -eq 0 ] && [ "$SZ" -gt 0 ] || echo "Codex 검증 미실행 — codex.err를 읽어라"
   ```

   `codex.err`·종료 코드·`codex.status`를 산출물 폴더에 보존하고, 사유를 사람 말로 적어 사용자에게 알린 뒤 다시 돌릴지 두 겹으로 진행할지 정한다(`SKILL.md` 4단계 (c)). 흔한 사유:

   - **종료 코드 127 / `command not found`** — `codex` CLI가 없다. 두 겹 상태다.
   - **`ran out of room in the model's context window`** — 먼저 **입력이 이 문서가 정의한 「한 대상」인지** 확인한다(아래 §한 대상의 범위). 평가 산출물 한 세트인데 넘쳤다면 세트를 나눠 각각 통째로 돌린다. 스킬 패키지 감사였다면 애초에 이 절차의 대상이 아니다(§범위 밖).
   - **그 밖의 비정상 종료** — 재시도 전에 `codex.err` 전문을 읽는다. 안전 차단에 걸린 것이면 **문구를 바꿔 우회하지 말고** 멈추고 사람에게 판단을 넘긴다.
   - **종료 코드 0인데 0바이트** — 조용한 실패다. 성공으로 세지 않는다.
1. 전문을 읽는다. 요약만 보고 판단하지 않는다.
2. **A급 지적은 반드시 반영한다.** 다만 반영 전에 원문을 직접 확인한다 — Codex가 파일의 다른 조항을 놓쳤을 수 있다.
3. B·C급은 적대적으로 재검증한 뒤 반영한다. 문서 구조를 바꾸는 권고(채점 요소를 더 잘게 쪼개라, 배점을 재배분하라, 평가 시간을 늘려라)는 **사용자 판단으로 남기고 보고만 한다.**
4. 반영 후 다시 빌드하고 검증기를 돌린다. 수정이 다른 곳을 깨뜨렸을 수 있다.
5. Codex 리뷰 전문을 위키나 산출물 폴더에 보존한다.

## 한 대상의 범위

**하나의 검토 대상 = 슬롯 JSON 한 개로 표현되는 평가 산출물 한 세트**다. 문항지 한 벌의 과제 개요·성취기준·문항 정보·학생 지면(도입·자료·발문·조건)·예시답안·채점기준표·유의점·성취수준 구간·차시 계획 **전부**이며, 실물은 `make_review_input.py`가 만든 `review_input.txt` **한 파일**이다. 크기의 눈금은 4문항 20점 기준 **50KB 안팎·슬롯 키 70개 안팎**이다.

**이 대상은 쪼개지 않는다. 통째로 한 호출에 준다.** 발문·조건·예시답안·채점기준·유의점·성취수준 구간의 **상호 정합**이 검토의 핵심인데, 쪼개면 그 사이의 어긋남을 아무도 보지 않는다. 「수학 검토」와 「채점기준 검토」로 나누고 싶은 유혹이 정확히 이 실패를 만든다. 한 세트는 한 창에 들어간다 — 컨텍스트를 아끼려고 나누지 마라.

한 호출에 주는 양이 이 눈금을 크게 벗어나면(예: 문항 세트 두 벌 이상을 합본, `review_input.txt`가 150KB를 넘음) 그것은 이미 **세트 하나가 아니다.** 세트 단위로 나눠 각각을 통째로 검토하고, 세트 사이의 총점·성취기준 중복만 그것만 보는 호출로 따로 대조한다. 세트 **안**을 가르는 분할은 여전히 하지 않는다.

## 병렬 사용

**독립된 대상이면** 여러 Codex 호출을 **한 메시지에서 동시에** 띄운다(예: 제출용 세트와 추가 문항 세트를 각각). 각 호출은 자립적이어야 하고(호출 간 기억이 없다 — 검토 관점·출력 형식·절대경로·확정 수치를 매번 인라인한다), **산출 파일 이름을 호출마다 다르게 준다.** 같은 이름으로 리다이렉트하면 서로 덮어쓴다. 부분 호출 몇 개가 성공했다고 전체 검증 통과라고 하지 않는다 — 하나라도 §결과 처리 0번에 걸리면 그 대상은 미검증이다.

## 범위 밖 — 스킬 패키지 감사

아래는 **평가 산출물 개발 절차가 아니라** 이 스킬의 도구·문서를 점검하는 유지보수 절차다. 위 「쪼개지 않는다」 규칙을 여기에 적용하지 않고, 반대로 **여기의 분할을 산출물 검토의 일반 권장으로 읽지 마라.** 평가 세트를 코드/채점/문서처럼 나누면 전체 정합 검사가 사라진다.

파일 십수 개·수백 KB를 한 프롬프트에 밀어 넣으면 `ran out of room in the model's context window`로 죽고 **산출이 0바이트**로 나온다(스킬 전체 18개 파일을 한 번에 감사시켰다가 실제로 겪었다). 이때만 서로 독립인 축으로 쪼개 병렬로 부른다.

쪼갤 때 지키는 것:

- **축은 서로 독립이어야 한다.** 축을 가로지르는 대조(예: 문서가 선언한 규칙 ↔ 코드가 실제로 검사하는 규칙)는 어느 호출도 보지 못한다. 그 대조가 필요하면 **그것만 하는 호출을 하나 더** 만들고 읽을 파일을 그 둘로 못 박는다.
- **읽을 파일을 이름으로 못 박는다.** "스킬 폴더를 훑어보라"고 하면 다 읽다가 한도를 넘는다. 파일 목록을 절대경로로 주고, 긴 파일은 볼 절까지 지정한다.
- 호출마다 §병렬 사용의 규칙(자립적 프롬프트, 서로 다른 산출 파일 이름)과 §결과 처리 0번의 종료 코드·크기 검사를 **각각** 적용한다.
